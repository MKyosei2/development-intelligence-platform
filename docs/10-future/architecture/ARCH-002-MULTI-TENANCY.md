# ARCH-002: 組織・プロジェクト分離と権限制御

**Status: Proposed.** 単一テナントかマルチテナントかを含め、提供形態は未決定。

## 1. リソースの階層（候補）

`Tenant -> Organization -> Team -> Project -> Revision -> Evidence/Artifacts/Jobs`

全リソースにTenantおよびProjectの所有関係を持たせ、API・DB・Artifact・ジョブを通じて境界を維持する。単純なUI非表示だけで認可したことにはならない。

## 2. 境界で考慮すること

- API: 操作のたびにActorとProject権限を検査する。IDを知っているだけでアクセスさせない。
- DB: クエリ条件にテナント境界を適用し、必要ならRLSを比較検討する。
- Artifact: 署名URL・保持期間・アクセス監査・オブジェクトキー分離を検討する。
- Queue/Worker: ジョブの実行者・入力・出力が別のテナントへ漏れないようにする。
- AI: モデルへ送るコードやログは契約、同意、秘匿化に従う。入力のプロンプトインジェクションを権威ある指示と見なさない。
- Logs/Tracing: 認証情報や未公開ソースを既定で出力しない。

## 3. モデルの選択肢

| 選択肢 | 長所 | リスク・検討点 |
|---|---|---|
| テナント別の独立インスタンス | 分離が明確 | 運用・費用増加 |
| 共通サービス＋論理的データ分離 | リソース効率 | 認可の漏れ、クエリ／キャッシュの横断リスク |
| 機能別の混合方式 | 重要データだけ強い分離 | 構成複雑性 |

**Decision:** 未決定。セキュリティ検証と導入条件を比較しRFC/ADRで判断する。

## 4. 検証ケース

他テナントIDの直接指定、ページング、検索、Artifactの署名URL再利用、ジョブ再試行、キャッシュ、バックアップ復元、ログ照会を負例としてテストする。

## 5. Exit criteria

脅威モデル、権限表、拒否ケースのE2E、認証の秘密管理、監査範囲、削除条件が合意されるまでは商用マルチテナント対応を宣言しない。
