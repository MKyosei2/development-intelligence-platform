# DIP 製品・技術ロードマップ案

**Status: Proposed.** 日付・バージョンは確約しない。実際のIssue／Milestone／Projectで更新する。

## 優先順位の判断軸

1. 実コードと実環境の検証差分が大きい項目を先に解消する。
2. 実利用者・再現可能なサンプルで製品価値を検証する。
3. Evidence、セキュリティ、データ隔離を後付けにしない。
4. 任意の高度な機能が、基本動作の信頼性を阻害しないようにする。

## Phase A — 実証可能なQAとEvidence

- 実UnityプロジェクトのEditMode/PlayMode/Buildを行い、SHA付きEvidenceを保存する。
- 実AI API経路をopt-inで実行し、生成案・隔離テスト・人間による承認の一連の挙動を測る。
- 独立した正常系・異常系・未知ケースで検出率と誤検知率を測定する。
- 現在のコードにある契約上の検査と、実行できる実検査を明確にする。

**出口条件:** 条件固定・手順公開・対象SHA・テスト結果・既知の限界が揃う。

## Phase B — ゲーム制作現場に近い検証

- Unityに続きUnrealの実エディタ／ビルド経路を検証する。
- GPU・グラフィックス・アセット・マルチプレイヤー・長時間負荷の代表サンプルを設ける。
- 失敗時の証拠、再現条件、計測誤差、未評価範囲を可視化する。

**出口条件:** サンプルプロジェクトごとに何を検査し何を検査できないかが測定できる。

## Phase C — 組織・運用の基盤

- 認証・認可・組織分離・秘密情報管理・ジョブ隔離の脅威モデルを検証する。
- 可観測性、バックアップ復元、異常時のフェイルセーフ、容量計画を定義・検証する。
- 操作監査、権限による情報マスキング、リリース承認手順を整備する。

**出口条件:** 障害試験・復旧試験・データ漏えい対策のEvidenceが確認できる。

## Phase D — サービス化の検討

- 利用者ヒアリング、導入試験、費用・サポート・契約責任を具体化する。
- 段階的なロールアウト、カナリア、ロールバックを実運用相当の環境で検証する。
- 合意したSLOをもとに24時間365日の運用可能性を評価する。

**出口条件:** 実運用の計測と運用体制を満たした範囲でのみ本番提供を主張する。

## 計画の管理方法

- GitHub Projects: 優先順位・ステータス・横断的なWorkstream管理
- Issues: 具体的な作業と受け入れ条件
- Milestones: 到達条件が定義されたリリース単位
- RFC: 技術方針が未決定の提案
- PR: コード・仕様の変更履歴と検証
