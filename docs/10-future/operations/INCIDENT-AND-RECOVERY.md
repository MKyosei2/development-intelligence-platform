# インシデント管理・バックアップ復元構想

**Status: Proposed**

## 1. 重大度と記録

Severityをユーザー影響、情報漏えい、データ整合性、サービス停止で定義する。発生時刻、検出時刻、影響、一次対応、復旧結果、対象システムのSHA、根本原因、再発防止Issueを記録する。

## 2. 必須の回復シナリオ

- DBのバックアップから別環境へ復元し、スキーマと参照整合性を確認する。
- Artifact Storeのオブジェクトとメタデータの整合性を検査する。
- Workerの中断・再起動で同じ処理が重複して確定しないことを確認する。
- Migration失敗時の復旧／ロールバックの条件を定める。
- 権限設定の変更や認証情報の漏えい時にアクセスを無効化できる。

## 3. RTO/RPO

RTO（許容復旧時間）、RPO（許容データ損失）を用途・顧客との合意から決める。現時点では数値未定。バックアップ取得成功だけでRestore Verifiedとしない。

## 4. セキュリティインシデント

不審なRunner実行、秘密情報の漏えい疑い、クロステナントアクセス、成果物改ざんは、通常の製品バグとは別に封じ込め・調査・通知方針を持つ。実データでの訓練に使う前に許可を取得する。

## 5. Postmortem

タイムライン、観測上のギャップ、組織的／技術的原因、再発防止Issue、受け入れテストを記録する。個人評価や責任追及のためのスコアリングは行わない。
