# 運用設計案：SLI / SLO / Alert / On-call

**Status: Proposed** | **Not production ready**

## 1. 目的

ユーザーに影響するサービスの品質を測り、障害時に原因と対処を追跡できるようにする。24時間365日運用は将来目標であり、現時点でSLOを達成した事実は示さない。

## 2. SLI候補

| SLI | 観測値 | 注意点 |
|---|---|---|
| API Availability | 成功と定義したリクエスト／対象リクエスト | ユーザーの4xx誤入力をどう扱うか定義 |
| API Latency | ユーザー影響があるエンドポイントp95/p99 | リクエストの種類を分離 |
| Job Completion | 期限内に正しく完了したジョブ率 | 不正なジョブは成功率に混ぜない |
| Evidence Integrity | 必須digest・対象SHA検証を通過した率 | 検証なしの保存を成功としない |
| Recovery | 障害からの復旧までの時間 | 復旧の完了条件を固定 |
| Data Durability | 復元試験での整合性 | バックアップがあるだけでは不足 |

## 3. 目標数値の決め方

最初は実運用に近い負荷と障害試験のベースラインを作り、顧客への影響・保守要員・費用を踏まえてSLOを決定する。現時点では`TBD`。恣意的な「99.99%保証」などを記載しない。

## 4. Runbookの最低限

- 発火条件・Severity・影響範囲・担当者
- 確認するDashboards / Traces / Job IDs
- 一時封じ込めと恒久対策を区別した手順
- データ破壊や二重実行を防ぐチェック
- Rollback、復元、ユーザーへの連絡、事後レビュー

## 5. 検証

API停止、DB接続断、WorkerのLease喪失、Artifact書込み不可、隔離Runner不在を注入し、検知・通知・復旧記録と実際の影響を検証する。
