# DIP 製品ビジョン：開発の進捗と品質をつなぐ基盤

**文書状態:** Proposed | **対象:** 将来の製品構想 | **非主張:** 商用提供・実稼働を保証しない

## 1. 解決したい課題

ゲームやソフトウェアの制作では、Issue管理、Git、CI、ゲームエンジン、性能測定、QA結果が別々のシステムに分散しやすい。タスクの「完了」やCI成功が、必ずしも実際の作品品質・動作保証を意味するわけではない。DIPはこれらを一意のProjectと改訂版（revision）に紐付け、説明可能な意思決定を支援する。

## 2. 長期ビジョン

大規模なゲーム・エンタメ制作チームから個人開発者までが使える、制作進行・技術QA・検証／リリースを横断する開発支援サービスへ育てる。将来的な24時間365日のサービス提供は**目標**であり、現時点での本番稼働実績ではない。

## 3. 三つの柱

| 柱 | 問題 | 将来の提供価値 |
|---|---|---|
| Project Truth / Evidence | 進捗申告と実際の品質が食い違う | Claim・Evidence・revisionを照合し、矛盾の理由を追える |
| Game Development QA | コード、描画、音声、性能、ゲームエンジンの検査が分散 | 多様な検査を共通プロジェクトに束ね、再現性と検査範囲を明示する |
| Verification / Release Operations | リリース判断が古いテストや属人的な経験に依存 | 必須検証・承認・リリース成果物を同じ改訂版へ結び付ける |

## 4. 想定する利用者

- **個人制作者:** 小規模プロジェクトでも検査漏れと環境差異を把握したい。
- **ゲームエンジニア・QA担当:** 再現条件、ログ、クラッシュ、描画差異、修正前後を一貫して追いたい。
- **テクニカルアーティスト・アーティスト:** アセット・シェーダー・描画負荷のリグレッションを検出したい。
- **テックリード・プロデューサー:** 進捗申告と裏付けを分けてリスクを判断したい。
- **開発基盤／運用担当:** 障害復旧、権限制御、監査可能なリリース運用を構築したい。

## 5. 長期的な製品コンセプト

- Evidenceを中心にしたプロジェクト横断の技術情報収集
- AIが根拠を参照して調査・修正候補を提示するQA支援（自律的な無検証マージはしない）
- Unity、Unreal、一般のソフトウェア、外部CI・DCCツールへの段階的対応
- リアルタイム／非同期の品質サマリーとリリース可否判断
- 組織・プロジェクト間の適切なデータ隔離、可観測性、監査
- 契約形態や事業モデルは未決定であり、利用実証を通じて検討する

## 6. 非目標

DIPがGitHub/Jiraそのもの、ゲームエンジン、完全自律型のコードマージ基盤、人物評価装置を代替することは目指さない。AIモデルの断言も、検証済みEvidenceの代わりにはならない。

## 7. 成果の判断

機能数ではなく、**検査の再現性、誤検知の抑制、実環境での動作、リリース判断の説明可能性、運用時の安全性**で評価する。指標と検証計画は[verification/VERIFICATION-STRATEGY.md](verification/VERIFICATION-STRATEGY.md)を参照。
