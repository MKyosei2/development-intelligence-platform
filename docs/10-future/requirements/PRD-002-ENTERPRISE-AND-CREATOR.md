# PRD-002: 個人制作者から組織利用へ拡張する要件

**Status: Proposed** | **対象:** 将来の導入形態

## 1. 利用形態

| 形態 | 仮説としてのニーズ | 先に検証すること |
|---|---|---|
| 個人／小規模チーム | 導入と設定の容易さ | 単一プロジェクトのセットアップ手順と維持負担 |
| 部門・制作スタジオ | 複数チームの権限・成果物集約 | RBAC、監査、プロジェクト隔離、データ保有方針 |
| 多拠点・複数会社 | 越境データと契約・運用の制約 | 秘密管理、データ所在地、可用性・組織間共有の条件 |

## 2. 機能要求の候補

- 組織、チーム、プロジェクト、サービスアカウントの階層
- 最小権限のロールとスコープ（Viewer、Contributor、QA Lead、Release Approver、Adminなどは例）
- プロジェクト単位の保持期間、削除、エクスポート、監査ログ
- 内部／外部のEvidence共有制御と秘匿化
- 課金や利用量上限は事業化の判断後に仕様化（現時点で商用機能とは主張しない）

## 3. 利用規約・アセット取り扱いの検討点

ゲームのビルド、スクリーンショット、音声、ソース、クラッシュダンプには第三者の権利・個人情報・未公開素材が含まれ得る。保存時暗号化、アクセス制御、アップロードの同意、用途の限定、機密情報削除を設計審査の対象とする。

## 4. 導入フロー

`利用者の合意 -> 安全な認証 -> Project登録 -> 最小権限Collector接続 -> 初回テスト -> データ範囲確認 -> Evidence表示 -> 運用レビュー`

## 5. 受け入れ条件（初期案）

- 権限のない利用者が他プロジェクトのソース・ログ・Evidenceを参照できない。
- 権限変更がAPI、ダッシュボード、非同期Worker、Artifactに同時適用される。
- 隔離されたテスト環境でクロステナントアクセスの負例が自動検査できる。
- 重要操作（承認、秘密変更、データ削除）は監査可能。
- 管理者がサービス停止・退会後のデータ削除方針を説明できる。
